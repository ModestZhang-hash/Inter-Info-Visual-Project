# Topic 3A: pairwise trade-off views

## What is implemented

- Three scatterplots of `makespan_s`–`energy_j`, `makespan_s`–`mean_latency_s`, and `energy_j`–`mean_latency_s`. Every point represents one complete run of the selected frozen instance. Units and minimization direction are visible on both axes.
- Stable color and shape slots assigned by sorted `policy_config_id`, regardless of manifest array order, plus a text legend and selected `run_id` label. A dark marker outline denotes non-dominance in that **particular 2D projection**. A separate dashed gold halo denotes non-dominance across all three objectives. Selection has its own ring.
- Click or keyboard selection, Shift-add selection, and rectangular brushing on each plot. `app/shared/pair_scatter.mjs` accepts records, axes, labels, encodings, and callbacks, so 3B can reuse the same renderer for matrix cells. Selection uses `run_id` in `app/shared/state.mjs`, the shared interface for 3B views. Configuration filters only change visibility; they neither recompute dominance nor rescale axes. Users can edit or reset the explicit axis domains.
- A selected run's stored metrics, three projected classifications, full-space classification, deterministic witness `run_id`, and task-event stages. The witness panel lists both complete M/E/L vectors and marks each compared dimension as strictly improved, exactly equal, or equivalent within tolerance. If several candidates dominate, the smallest `run_id` by Unicode code-point order is the primary witness and the other IDs remain visible. Export of selected run records preserves their numeric values.
- Import of one-instance bundle JSON, with ID/reference, event-stage, energy-accounting, and metric-recalculation checks before anything is plotted. Incomplete or failed runs never get objective points. A default seven-candidate front appears only when a non-fixture instance has one complete run for each of seven declared configurations.

## Data and provenance

The initial `examples/3a-demo/bundle.json` and `task_events.jsonl` are built by `examples/3a-demo/build_demo.py` from the existing two-task contract sample. The seven fixed destination pairs are hand-selected to exercise the visual rules. They are **not** outputs of Random, Latency-first, Energy-first, Balanced, or DQN, and must not be used as RQ3 evidence. In this fixture, run F is dominated by G on M–E yet remains non-dominated in M–E–L because its mean latency is lower. The UI labels every fixture view as a mathematical demonstration rather than an experimental Pareto front.

The bundle structure is:

```json
{"schema_version":"1.0.0","manifest":{},"instance":{},"runs":[],"events":[]}
```

Each nested object follows `docs/data_contract.md`. `scripts/build_3a_bundle.py` reads an archived manifest, its relative instance/run paths, and each run's JSONL event log, then writes a bundle for one `instance_id`. It does not modify the source archive. The bundle also contains `pareto_check` from `src/topic3/pareto.py`; the browser compares its own result and all witness details against that independent Python calculation. A bundle with fewer than seven declared complete candidates remains inspectable, but has no official dominance labels. A non-fixture full set requires the Python check to show official labels. The browser reads the imported file locally.

## Design checks and limits

`node --test tests/3a.test.mjs tests/3a_startup.test.mjs` and `python -m unittest discover -s tests -p 'test_*.py'` check strict and tied dominance, both possible 2D/3D disagreements, witness ordering and relations, absolute/relative tolerance, failed runs, instance isolation, record and plot values, click/brush IDs, filter invariance, Python/JavaScript agreement, and application initialization from the demo bundle. The viewer's event checks enforce local `null` transfer stages, nonlocal upload/compute/return order, and the manifest's active-compute and transfer-energy formulas.

The proposal says a three-objective dominated run cannot be non-dominated in a two-objective projection. That assertion has an equality exception: if the dominating run is exactly equal on both displayed axes and strictly better only on the hidden third axis, the projection contains a tie and neither point dominates there. The classifier and tests follow the formal dominance definition, including this case.

The existing app uses dependency-free SVG and JavaScript instead of introducing Dash/Plotly. This keeps the existing shared state and a reusable renderer; click and brush IDs are checked with the bundled sample. Browser rendering must still be checked in the target environment.

The 3A code is ready to consume P1–P3 records, but the repository currently supplies only hand fixtures. The independent Python Pareto implementation and a simulated-DOM startup/click/brush check are in place. Full P6 project acceptance still requires seven validated scheduler outcomes for a frozen instance, joint A/B review of `docs/data_contract.md`, real-browser visual and interaction checks, and cross-view checks with the later 3B interface. These are recorded dependencies, not claims of completed experiments or user validation.
